# Lab5 Git 协作流程

## 1. 基本规则

`lab5` 是集成分支，必须随时保持可运行。实际功能开发在个人功能分支完成，最后由罗茜统一合并和验收。

| 成员 | 工作分支 | 主要内容 |
|---|---|---|
| 石欣哲 | `feat/lab5-proc-sxz` | 进程启动、`exec/load_icode` |
| 贺佳怡 | `feat/lab5-mm-cow-hjy` | 普通 fork、内存复制、COW |
| 罗茜 | `feat/lab5-trap-syscall-lqx` | trap、系统调用、进程生命周期、集成 |

规则：

1. 石欣哲和贺佳怡不得直接向 `lab5` 提交功能代码。
2. 三人不得创建新的 `lab5` 分支，也不得修改他人的同名个人分支。
3. 罗茜负责把个人分支合并到 `lab5` 并推送。
4. 接口文件由对应负责人修改；接口变化必须遵守 `接口约定.md`。
5. 任何人发现他人模块的问题，先提交复现步骤，由原负责人修复。

## 2. 第一次建立个人分支

从最新的远端 `lab5` 建立自己的分支。

石欣哲：

```bash
git fetch origin --prune
git switch -c feat/lab5-proc-sxz --track origin/lab5
git push -u origin feat/lab5-proc-sxz
```

贺佳怡：

```bash
git fetch origin --prune
git switch -c feat/lab5-mm-cow-hjy --track origin/lab5
git push -u origin feat/lab5-mm-cow-hjy
```

罗茜：

```bash
git fetch origin --prune
git switch -c feat/lab5-trap-syscall-lqx --track origin/lab5
git push -u origin feat/lab5-trap-syscall-lqx
```

个人分支第一次推送后，远端会保存对应分支。

## 3. 开始开发前

每次开始写代码前，先同步集成分支：

```bash
git fetch origin --prune
git merge origin/lab5
```

不要直接在 `origin/lab5` 上修改。先切回自己的分支：

```bash
git switch feat/lab5-proc-sxz
```

其他人把分支名替换成自己的。

## 4. 开发和提交

### 4.1 提交粒度

每个提交只完成一个明确功能。推荐提交信息：

```text
lab5: implement trap entry and return
lab5: implement syscall dispatch
lab5: implement process startup
lab5: implement exec and ELF loading
lab5: implement fork and vm copy
lab5: implement copy-on-write
lab5: implement process wait and exit
lab5: add lab5 tests
```

禁止使用以下提交方式：

- 一次提交包含数天、多个模块的全部修改。
- 对整个文件做无关的格式化。
- 提交 `obj/`、`bin/`、日志、截图缓存和编辑器配置。
- 把多个人的代码混在同一个个人分支中提交。

### 4.2 每次提交前

```bash
git status
git diff
git add <具体文件>
git commit -m "lab5: 本次完成的单一功能"
```

确认没有误加入：

- `code/obj/`
- `code/bin/`
- `*.o`
- `*.log`
- `.vscode/`
- `.DS_Store`

### 4.3 推送个人分支

第一次：

```bash
git push -u origin feat/lab5-proc-sxz
```

后续：

```bash
git push
```

如果 git 提示远端有更新，先执行：

```bash
git fetch origin
git merge origin/lab5
```

解决冲突后再推送。不要使用 `git push --force` 覆盖个人分支，除非罗茜明确确认。

## 5. 个人测试门槛

每个功能分支至少通过自己的最小测试，才能交给罗茜合并。

### 石欣哲的分支

- 代码能够编译。
- `alloc_proc`、`kernel_thread` 和基本执行上下文可用。
- `hello` 能进入用户态。
- `exec/load_icode` 地址映射、用户栈和 trapframe 参数正确。

### 贺佳怡的分支

- 普通 fork 的全部现有测试通过。
- `badarg`、`forktest` 通过。
- 普通 fork 通过后，COW 才提交合并测试。
- COW 测试覆盖共享、首次写、双方写、退出回收和失败回滚。

### 罗茜的分支

- trap 能从用户态进入内核并返回用户态。
- 用户态 `ecall` 后返回地址正确。
- 全部系统调用可以正确分发。
- `exit/yield/kill/wait` 的基本测试通过。

测试必须保存命令、关键输出和失败复现步骤。

## 6. 交给罗茜合并

个人分支完成后，向罗茜提供：

```text
分支名：
最新 commit：
完成内容：
已运行的测试：
未解决的问题：
```

示例：

```text
分支名：feat/lab5-proc-sxz
最新 commit：a1b2c3d
完成内容：实现 alloc_proc、kernel_thread、exec 和 load_icode
已运行的测试：make、hello、exit
未解决的问题：无
```

不要只说“推上去了”，必须说明分支名、提交和测试结果。

## 7. 罗茜的集成分支操作

### 7.1 合并前

```bash
git switch lab5
git fetch origin --prune
git pull --ff-only
git status
```

工作区必须干净，`lab5` 必须和 `origin/lab5` 一致。

### 7.2 合并个人分支

推荐通过 GitHub Pull Request 合并到 `lab5`。如果不使用 PR：

```bash
git merge --no-ff origin/feat/lab5-trap-syscall-lqx
git merge --no-ff origin/feat/lab5-proc-sxz
git merge --no-ff origin/feat/lab5-mm-cow-hjy
```

合并后先测试，再推送：

```bash
git push origin lab5
```

不得在测试失败时把 `lab5` 推成不可运行状态。

### 7.3 合并顺序

1. `feat/lab5-trap-syscall-lqx`：先建立 trap 和系统调用基础。
2. `feat/lab5-proc-sxz`：接入进程启动、`exec/load_icode`。
3. `feat/lab5-mm-cow-hjy` 中的普通 fork 提交。
4. `feat/lab5-mm-cow-hjy` 中的 COW 提交。

COW 必须在普通 fork 全部通过后再合并。

## 8. 冲突处理

### 8.1 原则

- `code/kern/process/proc.c` 允许三人修改，但每人只能修改自己负责的函数。
- 不对整个文件格式化，减少无关冲突。
- 冲突出问题必须由“发生冲突函数的负责人”给出正确实现。
- 修改接口时由接口负责人同时修改声明、调用方和文档。

### 8.2 常见冲突

| 文件 | 冲突来源 | 处理人 |
|---|---|---|
| `proc.c` | 启动、fork、exit 都在此文件 | 各函数负责人 |
| `vmm.c` | 普通 fork 与 COW 缺页 | 贺佳怡 |
| `trap.c` | 系统调用和缺页入口 | 罗茜 |
| `proc.h`、`vmm.h` | 公共签名 | 对应接口负责人 |
| `report/` | 多人写报告 | 罗茜统稿 |

解决冲突时：

1. 先确认对应接口约定。
2. 保留每个函数唯一负责人的实现。
3. 不删除 `lab5` 注释。
4. `YOUR CODE` 只替换为负责该函数的成员学号。
5. 解决后重新编译和测试，再提交合并结果。

## 9. 集成分支测试

罗茜每次合并后至少执行：

```bash
cd code
make
make grade
```

根据合并内容增加定向测试：

- trap/syscall：`badsegment`、`divzero`、`softint`
- exec：`hello`、`pgdir`、`testbss`
- fork/COW：`badarg`、`forktest`、COW 自定义测试
- 生命周期：`exit`、`spin`、`yield`

最终验收还必须覆盖：

- gcc 15.1.0
- gcc 13.2.0 + QEMU 8.2.2
- gcc 10.2.0 + QEMU 4.1.1

## 10. 禁止事项

禁止：

- 直接向 `lab5` 推未经验证的功能代码。
- 把个人分支直接删除，导致提交无法追溯。
- 用强推覆盖 `lab5`。
- 把别人的提交重写成自己的提交。
- 在个人分支上修改接口但不通知其他两人。
- 把 COW 和普通 fork 的基础修复混成一个无法定位的提交。
- 删除或覆盖老师提供的 `lab5` 注释。

## 11. 最终提交流程

1. 三人确认个人分支均已推送。
2. 罗茜合并全部内容到 `lab5`。
3. 执行全量测试。
4. 检查 `report/` 中分工、接口、流程、报告和测试记录。
5. 检查 `code/` 中没有构建产物。
6. 检查最新 `lab5` 能从远端重新克隆并构建。
7. 罗茜最后推送并通知全组。

最终状态：

```text
lab5                 集成分支，只由罗茜更新
feat/lab5-proc-sxz   石欣哲的开发记录
feat/lab5-mm-cow-hjy 贺佳怡的开发记录
feat/lab5-trap-syscall-lqx 罗茜的开发记录
```
